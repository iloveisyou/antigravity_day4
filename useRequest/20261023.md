## 1. 오늘의 작업 1: 로컬 로그인 무한 튕김 오류 원인 및 해결

### 1) 현상
- 로컬 서버(`http://localhost:3000`)에서 정상 계정(`user@mindflow.com`)으로 로그인하면, 1초 만에 다시 로그인 폼으로 튕겨나가는 현상 발생.

### 2) 숨겨진 근본 원인
1. **`.env` 파일에 100% 구형 레거시 키 잔존**:
   - 로컬의 `.env` 파일에 소멸된 옛날 Supabase(`ylhbaiolxexzkuinsprj`) 주소와 키가 그대로 남아있었습니다.
2. **JWT 키 필터링 결함 (Base64 인코딩의 함정)**:
   - `api/_lib/supabase.js`에서 구형 키를 걸러내기 위해 `!key.includes('ylhbaiolxexzkuinsprj')` 평문 검색을 사용했으나, **JWT 토큰은 payload가 Base64로 인코딩되어 있어 평문이 존재하지 않아**(`InlsaGJhaW9seGV4emt1aW5zcHJq`로 변환됨) 구형 키가 필터링을 뚫고 통과했습니다.
   - 이로 인해 신규 URL(`qzbkalpmjjfzroenmoyi`)과 구형 키가 조합되어 백엔드가 `{"details":"Invalid API key"}` (HTTP 401)을 냈습니다.
3. **프론트엔드의 즉시 강제 로그아웃**:
   - `app.js`의 `fetchHistory()`는 401을 받으면 즉시 `signOut()`을 호출하고 화면을 로그인 폼으로 돌려보냈기 때문에, 로그인 직후 1초 만에 강제 로그아웃되고 튕겨나갔던 것입니다.
4. **구형 로컬 프로세스(PID 10572) 잔존**:
   - 어제 오후 4:25에 기동된 `vercel dev`가 종료되지 않고 메모리에 옛날 모듈 설정을 물고 있었습니다.

### 3) 조치 내역
- **`.env` 및 `.env.example` 동기화**: 신규 Supabase(`qzbkalpmjjfzroenmoyi`) 및 신규 Redis 정보로 100% 일치화 완료.
- **JWT payload ref 디코딩 검증 도입 (`api/_lib/supabase.js`)**: Base64 디코딩을 통해 `payload.ref === 'qzbkalpmjjfzroenmoyi'`인 정품 키만 통과시키도록 방어 로직 전면 개편.
- **프론트엔드 무한 튕김 방어 (`app.js`)**: 401 에러 중 서버 설정 오류(`Invalid API key`)인 경우 사용자 세션을 강제 파기하지 않도록 분기 처리.
- **프로세스 재기동**: 어제자 프로세스(PID 10572) 종료 후 신규 프로세스로 로컬 서버 정상화 완료.

## 2. 오늘의 작업 2: 무료 서비스 365일 영구 유지(Keep-Alive) 시스템 구축

### 1) 구축 배경
- **Supabase 무료 티어**: 7일 동안 API 호출이나 쿼리가 없으면 프로젝트가 **자동 일시중지(Paused)** 상태가 됨.
- **Upstash Redis 무료 티어**: 30일 동안 명령어가 없으면 데이터베이스가 비활성화/삭제됨.
- **문제점**: 사용자가 컴퓨터를 끄거나 몇 주 동안 접속하지 않으면 로컬 에이전트도 함께 잠들기 때문에, 클라우드 상에서 24시간 365일 알아서 동작하는 자동화 장치가 필수적임.

### 2) 해결 방안: 클라우드 이중 안전망(Dual Safety Net)
사용자의 컴퓨터가 완전히 꺼져 있어도, **GitHub Actions**와 **Vercel Cron**이 매주 자동으로 깨어나서 배포 사이트의 헬스체크 API를 호출하여 Supabase와 Redis에 활동(Activity)을 기록합니다.

---

## 3. 자동화 시스템 구성 상세 (이중 안전망)

```
                     [GitHub Actions 클라우드 러너]
                 (매주 월, 목 한국시간 09:00 자동 실행)
                               │
                               ▼
               [GET https://antigravity-day4.vercel.app/api/keep-alive]
                               │
            ┌──────────────────┴──────────────────┐
            ▼                                     ▼
     [Supabase DB]                           [Upstash Redis]
(SELECT count 쿼리 1회 실행)                 (PING 명령어 1회 실행)
 ──► 활동(Activity) 기록                    ──► 활동(Activity) 기록
 ──► 7일 자동 일시중지 원천 차단             ──► 30일 자동 소멸 방지
```

### ① 전용 헬스체크 API (`api/keep-alive.js`)
- 캐시 방지(`Cache-Control: no-store`) 헤더를 적용하여 매 호출마다 실제 DB와 통신.
- Supabase `messages` 테이블 레코드 수 조회 (`select('*', { count: 'exact', head: true })`).
- Redis `PING` 명령 전송 및 `PONG` 응답 확인.
- 서비스별 지연 시간(Latency) 및 타임스탬프를 JSON으로 응답.

### ② GitHub Actions 스케줄러 (`.github/workflows/keep-alive.yml`)
- **실행 주기**: 매주 월요일, 목요일 UTC 00:00 (한국 시간 오전 9시) 주 2회 자동 실행.
- **수동 실행 지원**: GitHub 웹 저장소의 Actions 탭에서 언제든 [Run workflow] 버튼을 눌러 즉시 수동 실행 가능.

### ③ Vercel Cron 스케줄러 (`vercel.json`)
- Vercel 자체 클라우드 스케줄러를 등록하여 GitHub Actions와 함께 이중으로 자동 호출 보장.

## 4. 검증 결과 및 수동 테스트 방법

### 1) 로컬 API 검증 결과
- 엔드포인트 직접 호출 결과:
  ```json
  {
    "timestamp": "2026-10-23T06:14:55.767Z",
    "status": "healthy",
    "services": {
      "supabase": {
        "status": "ok",
        "messageCount": 4,
        "latencyMs": 660
      },
      "redis": {
        "status": "ok",
        "response": "PONG",
        "latencyMs": 80
      }
    },
    "totalDurationMs": 741
  }
  ```
  - **Supabase**: 정상 활동 기록 확인 (지연 시간 660ms)
  - **Redis**: PONG 정상 응답 확인 (지연 시간 80ms)

### 2) 브라우저에서 직접 테스트하는 방법
배포 후 언제든 브라우저 주소창에 아래 URL을 입력하시면 실시간 상태를 확인하실 수 있습니다:
- URL: [https://antigravity-day4.vercel.app/api/keep-alive](https://antigravity-day4.vercel.app/api/keep-alive)
- 화면에 `status: "healthy"`, `supabase: "ok"`, `redis: "ok"` 가 출력되면 활동이 정상 갱신된 것입니다.
